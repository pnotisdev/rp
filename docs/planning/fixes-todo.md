### 0. No way to tell a message came from an Unlocks-tab action, after the fact

Live-verified against the actual chat; typecheck + full suite clean.

### 1+2. The two "model echoes something back verbatim as if it were a fresh reply" bugs
Fixed together — same root mechanism (`isUsableReply` in `runGeneration`, `useChatSession.ts`) covers both.

- **New `isDuplicateOfRecentText()` (`src/lib/text/slop.ts`)**: a bidirectional substring check (candidate contains an earlier text, or vice versa) against the last 6 messages from *either* role, gated on both texts being ≥40 chars so a legitimately-recurring short line ("...Fine.") is never flagged. Catches all 3 live-observed shapes at once: a tail-end-only repeat, a concatenation of the last two char turns, and a byte-for-byte copy of the *player's* own earlier line. A match now makes `isUsableReply` false — treated exactly like the existing empty/echo failure (marked `failed: true`, never reaches the judge).
- **The relationship-guidance leak specifically**: two new `META_LINE_PATTERNS` entries in `cleanModelOutput` strip the block's two most identifiable fixed lines outright (handles a *partial* leak mixed with real dialogue — the surviving dialogue stays intact). For the broader case (other lines of the same block — pacing/gift-taste notes — surviving alongside), `runGeneration` now reconstructs the exact `buildRelationshipDescription()` text that was actually injected this turn (same inputs, same macro substitution) and runs it through the same `isDuplicateOfRecentText` check.
- **Regenerate no longer double-counts a judge delta**: new `StoredMessage.relationshipJudged?: boolean` (`types.ts`) — the judge now fires **at most once per message id, ever**, on whichever attempt is the first to land usable text. A regenerate that produces a fresh (or another duplicate/failed) draft no longer reruns the judge and stacks a second delta on top of what the first successful attempt already applied.
- **Verification:** 16 new tests (`slop.test.ts`), full suite (1447 tests) + typecheck clean. Not live-verified end-to-end against the real backend (the exact failure is intermittent, and re-provoking it on demand would burn API calls without a guaranteed repro) — confidence instead comes from unit tests built directly from the exact text captured live earlier this session, plus careful review of the gating logic (the existing generation lock already serializes all calls per chat, so there's no race between the read-then-mark-judged steps).

### New, found by the user live: a drafted intimacy action can drift onto a completely different act than the one clicked
**Live catch:** clicking "a vibrator" from Unlocks mid-kiss produced a fluent, in-character reply that was just... more kissing — nothing about a vibrator at all — saved under the toy's own `intimacyAction` label with no way for anything to notice the mismatch (the new traceability badge from item 0 is what actually surfaced this: without it, this would've just read as slightly-off prose with no way to tell it was supposed to be about something else entirely).
**Root cause:** `draftIntimacyAction` (`useChatSession.ts`) told the model to write prose "fitting exactly where the scene already is" — with a strong kissing beat already in progress, that reads as license to keep doing that instead of switching to the newly-clicked action.
**Fix:** reworded the directive to state unmistakably that this is a deliberate change *from* whatever was just happening, not a continuation of it — the mood/position stay there to shape the transition, never a reason to substitute the old act for the new one. Typecheck + full suite clean.
**Not a full fix, worth knowing:** there's no deterministic way to verify a drafted line actually matches the clicked action (verifying topical relevance isn't a string match) — this is a prompt-engineering mitigation that should reduce drift, not eliminate it. The composer's own review-before-send step is still the real backstop; worth actually reading a drafted action against its own label before hitting send, especially mid-scene.

### 8. No post-generation check for a reply narrating the *user's* own climax/sensations
**Implemented:** new `detectPersonaClimaxNarration()` (`src/lib/dating/agencyGuard.ts`) — a deterministic, lexical, same-philosophy sibling to `boundaryGuard.ts`'s hard rail (false negatives preferred over false positives, never auto-rewrites). Deliberately narrow: only fires when the persona's name is closely, structurally anchored to an explicit climax phrase as its grammatical subject (`{Name} reached his/her/their climax`, `{Name}'s own climax/orgasm/release`, `{Name} orgasmed`) — not just co-occurring anywhere in the sentence. Caught and fixed two false-positive shapes during design itself before shipping: a possessive-on-name miss (`Kai's own orgasm`), and the more serious case of the persona's name appearing only as an unrelated possessive elsewhere in a sentence whose climax is plainly the *character's* own ("Sumire, still holding Kai's hand, reached her own climax" must never flag) — both have dedicated regression tests now (11 tests, `agencyGuard.test.ts`).
Wired into `useChatSession.ts` right alongside the existing `detectAnyBoundaryCrossing` check: sets a new durable `StoredMessage.povFlag` (mirrors `boundaryFlag`'s pattern exactly) plus a toast, never blocks or auto-regenerates. `povFlag: null` cleared at every site `boundaryFlag: null` already was (regenerate, steer, swipe-new, swipe-switch, hand-edit). New `AlertCircle`-icon badge in `MessageBubble.tsx` (all 3 chat styles), visually distinct from `boundaryBadge`'s triangle. Typecheck + full suite (1458 tests) clean. Not live-verified against the real backend — same reasoning as item 8 above in the 1+2 entry: the exact failure is a specific, hard-to-provoke-on-demand shape, and confidence instead comes from the design's own dedicated false-positive regression tests plus code review of the wiring.

### 11. Turn the "quick self-check" into a real, cheap post-hoc check
**Implemented, deliberately narrower than the original idea:** new `detectExplicitAntiPatternUsed()` (`src/lib/dating/intimacyScene.ts`, exported `EXPLICIT_ANTI_PATTERNS` alongside it) — a lexical, non-AI check for whether a peak-phase reply actually used one of the named stock phrases it was told to avoid. Same "cheap hard rail behind a prompt-side ask" pattern as `boundaryGuard.ts`/`agencyGuard.ts`. Wired into `useChatSession.ts` right alongside the boundary/POV checks: sets a new durable `StoredMessage.explicitQualityFlag` plus a toast, badge in `MessageBubble.tsx` (a `MessageSquareWarning` icon, distinct from the other two flags). `null`-cleared at all 5 sites the other flags already are.
**Deliberately did NOT implement the other half** ("include a concrete sensation" as a measurable rate) — that instruction is an *open* set (a good reply can be concretely physical using a sensation word never in any finite list this app could author), unlike the anti-pattern list (a closed, curated set of phrasings reliably bad wherever they appear). A presence-of-a-word check for the positive case would false-positive on perfectly good prose constantly — the exact "heuristic that flags ordinary scenes and trains the player to ignore the warning" failure mode this project's own hard-rail philosophy warns against. A real measure of that half needs actual judgment (a model call), which is out of scope for a "cheap" check; left for a future pass if ever worth the cost. 15 new tests (`intimacyScene.test.ts`), full suite + typecheck clean. Not live-verified against the real backend (same reasoning as item 8: a specific, hard-to-provoke-on-demand shape) — confidence from unit tests plus code review of the wiring.

### 12. A tiny escalation-shape memory
**Implemented:** new `RelationshipTrack.intimacySceneShapeLog` (`types.ts`) — a small, bounded (`SCENE_SHAPE_LOG_CAP = 3`), append-only log of the last few *resolved* scenes' own catalog-category sequence (e.g. `['kissing_spot', 'position', 'toy']`), same recency-not-lifetime-tally pattern `dating/gifts.ts`'s `giftLog` already established for a different repeat problem. `IntimacyScene.categoryHistory` (`intimacyScene.ts`) tracks the *current*, still-open scene's own in-progress sequence, threaded through `startOrShiftIntimacyScene`'s new optional `priorScene` param; snapshotted into the log the moment a scene actually resolves (`useChatSession.ts`'s `updateAffectionFromReply`). New `repeatedEscalationShapeGuidance()` fires a `styleGuidance` nudge for the whole duration of a new scene whenever the two scenes immediately before it traced the identical sequence — "the last two intimate scenes both moved through the exact same sequence... let this one actually diverge somewhere." Resolves to nothing the vast majority of the time (needs two truly identical resolved scenes back to back), so an ordinary chat pays nothing for it.
Stored as bare `string[][]` rather than `IntimacyCategory[][]`, same reason `StoredMessage.intimacyAction.category` already documents (avoids a circular import back through `intimacyCatalog.ts`). 24 new tests (`intimacyScene.test.ts`), full suite + typecheck clean. Not live-verified with a genuine repeated-shape scene (would need faking two full resolved scenes with an identical curve, which is exactly the kind of state-faking the user ruled out earlier this session) — confidence from unit tests, plus a live Prompt Inspector check confirming the line is correctly *absent* on the real, live chat's current single-scene state (nothing logged yet to repeat).

### 14. The 429 rate-limit error text overclaims permanence
**Implemented:** `OpenAICompatibleClient` (`openaiCompatible.ts`) never rewrites or drops a provider's own error message — it still carries real information — but now *appends* a hint on any 429: the provider's own `Retry-After` header, rendered as a real seconds/minutes figure, when one comes back; otherwise a soft, honest hedge ("this can sometimes clear on its own within a minute or two, despite the wording above") rather than silently trusting whatever permanence the provider's own wording implies. Applied to both `generate` and `generateStream`. 4 new tests (`openaiCompatible.test.ts`), full suite + typecheck clean.
